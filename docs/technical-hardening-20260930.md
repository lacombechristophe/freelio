## Démarrage et démonstration

Le périmètre actuel est « démo uniquement », confirmé par l’utilisateur. Utiliser `npm run demo` et le [guide local](demo-local.md) : le lanceur crée une copie séparée sans données du projet ni `.env`, et y applique son garde-fou réseau. Le flag de textes de démonstration seul ne bloque pas les fournisseurs ; le lanceur transmet aussi un environnement sans configuration fournisseur. La mise en service avec des données réelles reste distincte.

Avec les dépendances existantes, `npm run dev` déclenche la préparation normale de la base de développement. Ne pas lancer `npm run verify` sur une base partagée : ce script prépare la base configurée et exécute des tests qui écrivent.

`scripts/seed-demo.mjs` exige explicitement une SQLite dont le nom correspond à `demo*.db`, un `DEMO_PASSWORD` d’au moins 12 caractères et un environnement non production. Il ne charge aucun `.env`, ne supprime rien et refuse un second amorçage du même compte. Le schéma doit être créé au préalable dans cette base dédiée. Le compte synthétique est `direction@atelier-des-bassins.example.test`, avec six clients, devis, factures brouillons et interventions, trois produits et un dépôt. Les coordonnées sont marquées fictives ; aucune communication, intégration ou automatisation sortante n’est créée. Le mot de passe de recette a été aléatoire et non publié ; choisir son propre mot de passe lors de l’amorçage d’une nouvelle démo. Ne pas présenter la base de recette comme un compte hébergé accessible.

## Exploitation et récupération

1. Avant de déployer, sauvegarder la base et les objets, conserver séparément la clé de chiffrement, appliquer les migrations PostgreSQL, et exécuter les tests CI sur le SHA exact. Vérifier aussi les polices et la disponibilité de Chromium dans le runtime cible.
2. Pour une facture historique sans archive, récupérer le PDF/XML d’origine et leurs preuves d’identité. Ne pas générer une nouvelle version à partir des fiches actuelles et l’appeler original. La référence doit appartenir à l’entreprise et à la facture, son empreinte doit être vérifiée ; le processus de récupération reste à construire.
3. Pour un import interrompu doté d’un heartbeat, attendre l’expiration de 15 minutes puis relancer le même lot. Pour un ancien lot sans marqueur, inspecter objets, mappings et checkpoints avant une intervention ciblée. Une vérification verte n’autorise pas à elle seule une bascule complète.
4. Pour une sauvegarde en erreur, lire `failed` et `remaining`, contrôler les membres actifs, les fichiers manquants/altérés, le stockage, les limites et les appels planifiés. La date `lastBackupAt` indique un stockage réussi, pas une restauration démontrée. Le cron quotidien et le rattrapage GitHub doivent être supervisés ; leurs délais ne sont pas un SLA.
5. Pour restaurer, travailler dans une cible neuve, vérifier le manifeste et les objets, tester identifiants, relations et montants, puis produire un compte rendu avant bascule. Le format v4 ne promet pas de réinjection automatique. Une sauvegarde native PostgreSQL + objets et un exercice de restauration restent requis pour l’exploitation.
6. Les dépenses sont saisies manuellement et les justificatifs restent archivés. Gemini est retiré ; aucune facture n’a été envoyée à Google pendant la recette. Le téléchargement de polices publiques ne transmet pas les pièces métier.
