# Acquisition des images de recette Linux

Le commit documentaire `61d7331` conserve les sources métier qualifiées sur `d82ed46`. Sa [CI de branche](https://github.com/lacombechristophe/freelio/actions/runs/38050431853) réussit. Dans la [CI de PR](https://github.com/lacombechristophe/freelio/actions/runs/38050436373), qualité, navigateur et PostgreSQL réussissent ; le job Linux échoue deux fois sur `toomanyrequests: Rate exceeded` pendant le téléchargement de Redis, après construction de l'image applicative. La seconde tentative ne rejoue que ce job. Ces échecs restent des échecs : [résultats et empreintes des logs](quota-failures.json).

`scripts/runtime-images.mjs` prépare désormais PostgreSQL et Redis par empreinte d'index OCI, avec deux essais par registre, séparés de cinq secondes uniquement en cas de quota. Après deux refus de quota sur ECR Public, Docker Hub fournit une seconde source officielle du même contenu. Une autre erreur arrête immédiatement la recette. Les conteneurs utilisent `--pull never` après préparation. Aucune migration, création de données, commande de conteneur ou opération métier n'est rejouée par ce mécanisme.

Le [relevé des manifests](manifests.json) compare les index complets et leurs manifests Linux amd64 sur les deux registres. Les empreintes sont recalculées depuis les octets reçus, puis comparées aux en-têtes du registre. Le code épingle l'index complet, pas uniquement amd64. Cette lecture HTTP ne prouve pas l'exécution des images : celle-ci reste à qualifier dans la nouvelle CI Linux. Docker documente la [publication officielle sur ECR Public](https://www.docker.com/blog/news-from-aws-reinvent-docker-official-images-on-amazon-ecr-public/) et les [téléchargements par empreinte](https://docs.docker.com/reference/cli/docker/image/pull/).

Les sept tests de `tests/unit/runtime-images.test.ts` injectent téléchargement et attente : succès primaire, reprise sur quota, repli à empreinte identique, arrêt sur authentification/manifeste/réseau et épuisement borné des quatre essais. Aucun conteneur local n'est lancé. Le rapport `verification.json` de la recette conserve les tentatives, la référence retenue et l'identité de chaque image, y compris les tentatives précédant un échec.

Les neuf contrôles runtime existants restent requis. Les deux registres peuvent être simultanément indisponibles ou limités ; le job échoue alors sans masquer le résultat. L'épinglage nécessite une mise à jour volontaire lors de la maintenance des images : vérifier les nouveaux manifests sur les deux sources, modifier les empreintes, puis qualifier à nouveau la recette Linux. Il ne constitue pas un audit de vulnérabilités des images.
