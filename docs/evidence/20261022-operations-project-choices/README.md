# Choix Chantier des créations Opérations

Code : `a5cfdc29482b62d37221d12feeacb549ddef56da`. Les créations Commande client, Mouvement de stock et Intervention utilisaient `getOperationsDashboard().projects`, limité à 300 lignes. Le [diagnostic sur faf2f06](baseline.json) retrouve le 301e chantier dans la base, mais pas dans ce chargement. Trois assertions échouent — parcours complet, recherche et sélection hors chargement — pour une même limite ; un choix initialement visible reste disponible. Ce ne sont pas trois vulnérabilités indépendantes.

La [sonde conservée](baseline-probe.test.ts.txt) donne une forme commune à l’ancien tableau chargé ou au nouveau lecteur paginé. Elle vérifie les données consommées par les trois formulaires, sans exécuter leur interface. Les tests finaux appellent directement la nouvelle action. Le cache du tableau de bord reste limité pour ses autres consommateurs : ce lot ne corrige pas tous les indicateurs d’agence.

Le [lecteur](../../../src/lib/operations/project-choices.ts) applique recherche, total et pages de 25 au périmètre éligible. Les relations société/agence, site/client et modèle sont filtrées en SQL avant pagination. Le choix sélectionné est résolu séparément de la page et de la recherche ; seuls son identifiant et son libellé sont renvoyés. Le client limite les chantiers de la commande ; le site limite ceux de l’intervention à son client et aux chantiers sans site ou liés à ce même site. Les critères restent ceux des chantiers actifs, et un identifiant stabilise les noms identiques.

Les [trois formulaires](../../../src/app/dashboard/operations/operations-center.tsx) utilisent le même sélecteur natif, avec recherche, total et précédent/suivant. Le choix et les autres saisies restent dans le formulaire pendant la recherche ou un refus. Une vérification en cours, échouée ou devenue incompatible bloque l’enregistrement d’un chantier choisi ; l’utilisateur peut le remplacer ou le retirer lorsqu’il est facultatif. Les droits d’écriture métier ne changent pas.

Une première implémentation locale a échoué sur la démo publique : ses SELECT étaient refusés par le garde-fou SQL brut. Le [rapport intermédiaire](local.json) conserve cet échec sur 98 cas, puis les 99 et 112 cas réussis après correction. Il s’agit d’une erreur de cette implémentation, pas d’un défaut antérieur ni du harnais. L’exception porte sur le texte exact d’un des trois SELECT construits dans ce lecteur, sous contexte `operations.read` de la société et pendant sa seule exécution. L’appelant ne fournit aucun SQL. Les autres SQL bruts, les mutations et la fuite du contexte après lecture sont refusés dans les tests. La sonde de disponibilité `SELECT 1` conserve son fonctionnement.

## Reproduction

Dans une copie isolée déjà installée, avec secrets fictifs et une `DATABASE_URL` SQLite neuve, préparer la base par `node scripts/prepare-dev-database.mjs`, puis lancer `node node_modules/vitest/vitest.mjs run tests/unit/operations-project-choices.integration.test.ts tests/unit/reservation-choices.integration.test.ts tests/unit/asset-choices.integration.test.ts tests/unit/project-directory.integration.test.ts tests/unit/public-demo-database.integration.test.ts tests/unit/public-demo.test.ts --no-file-parallelism`. La suite complète utilise `run --coverage --no-file-parallelism`, sans build parallèle.

Pour le diagnostic, prendre une autre copie isolée de `faf2f06`, y copier la sonde sous `tests/unit/operations-project-choices.integration.test.ts`, préparer une nouvelle base fictive et lancer ce fichier. Trois échecs et un témoin positif sont attendus.
