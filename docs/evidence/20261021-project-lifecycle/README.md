# Chantiers : mutations, audit et versions affichées

Code : `a2884da` puis `9a2e6e6af93d92c7febb08f244a518abc3308ee5`. Le [diagnostic SQL](baseline.json) conserve la sonde initiale de 16 échecs, puis six cas de version affichée. Ce ne sont pas 22 vulnérabilités indépendantes : quatre cas initiaux vérifient des lectures métier précédant le refus d’écriture, déjà assuré par l’extension Prisma. Les témoins positifs vérifient aussi le fonctionnement attendu de la suppression et de l’archivage. Un échec intermédiaire du nettoyage des tests est identifié séparément.

Les [actions](../../../src/actions/projets/index.ts) exigent Opérations en écriture avant lecture métier. Création, étapes issues du modèle et audit partagent leur transaction ; modification, archivage et suppression relisent le chantier dans le périmètre société/agence et conservent leur audit dans la même transaction. Les références Client/Site/Modèle incohérentes sont refusées sans réparation historique. Un changement de client est refusé en présence de devis, factures, commandes client, récurrences, interventions, dépenses ou temps facturés. La suppression est refusée lorsqu’elle ferait perdre des documents, opérations, réservations ou temps facturés ; l’archivage conserve ces relations et ne libère aucun stock.

Les métadonnées des fichiers et temps non facturés sont supprimées avec le chantier, puis les fichiers physiques sont purgés après commit. Chaque chemin doit appartenir au dossier de ce chantier et de sa société, sans traversée ; une référence ancienne non qualifiée est conservée et nécessite une vérification. Une panne de stockage renvoie une suppression SQL réussie et le nombre de pièces restant à purger ; la notification existante signale ce reste. L’audit transactionnel conserve toutes les références ; un audit complémentaire d’échec est tenté. Il n’existe pas encore de worker durable de purge ni de reprise garantie après arrêt brutal.

Le [lecteur de liste](../../../src/actions/projets/directory.ts) fournit `updatedAt`. Les formulaires, archivages et confirmations de suppression transmettent cette version ; un décalage est refusé avant changement. Une modification valide fait avancer la version. Le message conserve la saisie ; la [recette navigateur préparée](../../../tests/e2e/project-lifecycle-conflicts.spec.ts) vérifie ce comportement sur ordinateur et mobile. Elle est sélectionnée, pas exécutée. La version porte sur les champs du chantier, pas sur chaque enfant de son dossier.

La [recette locale](local.json) passe **3 406 tests dans 274 fichiers**, sans échec ni exclusion, sur une SQLite fictive neuve. Les 37 cas dédiés et 49 voisins passent dans cette même exécution. Manifeste exact et 1 212 fichiers source conformes au commit ; types, ESLint, Oxlint et build de 76 pages passent. Les sept contrôles du générateur/PDF natifs restent inclus. La couverture concerne les six modules configurés, pas toute l’application. **468 cas Playwright sélectionnés, 234 par surface ; aucun parcours applicatif exécuté.**

Les 46 cas de cette suite passent isolément, puis la suite complète est relancée sur une nouvelle base sans build parallèle. La cause du dépassement n’est pas établie ; ni test ni délai n’ont été modifiés. Les deux résultats sont conservés dans la preuve.

SQL, adhésions et droits sont réels ; session/cache et suppression physique des fichiers sont simulés dans les tests Chantiers. Les refus d’audit et de suppression utilisent de vrais déclencheurs SQL. Concurrence native PostgreSQL, Linux, interactions navigateur et stockage réel restent à qualifier. Aucune migration, sortie fournisseur, nouvelle CI, fusion ou publication.
