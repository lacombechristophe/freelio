# Refuser un aperçu des temps devenu périmé avant soumission

Lot approuvé le 13 octobre 2026. Le correctif transactionnel compare la préparation serveur avec les valeurs relues dans sa transaction. Ce complément compare aussi cette préparation avec les valeurs déjà affichées dans un ancien écran.

Le diagnostic charge une heure, calcule l'aperçu avec le même constructeur de lignes que le formulaire (100 € HT), puis modifie réellement le temps à deux heures avant l'appel de facturation. Le brouillon créé vaut 200 € HT : son calcul est juste pour les données courantes, mais différent de l'aperçu initial. Il n'y a aucun entrelacement pendant la transaction dans ce cas.

Conserver avec les données affichées une version des temps et des paramètres financiers préparée par le serveur. La soumission doit identifier cette version pour chaque temps sélectionné ; le serveur la vérifie avant calcul et création, puis garde son recontrôle transactionnel. Une version absente, différente ou devenue inaccessible doit empêcher une création sur un aperçu ancien. Ce marqueur ne donne aucun droit et ne remplace ni les montants recalculés, ni l'autorisation Finance/société/client/chantier/agence.

Réutiliser « Les temps ont changé pendant la création de la facture. Rechargez la page puis réessayez. » et conserver sélection, taux, mode, objet et échéance. Aucun champ, bouton, couleur ou placement nouveau. Un rechargement récupère les valeurs courantes ; le serveur ne remplace pas silencieusement la saisie. Aucun brouillon, rattachement ni audit après refus ; la modification légitime des temps reste conservée. La démo publique demeure en lecture seule.

Recette prévue : modification avant soumission de durée/date/texte/rattachement/facturabilité, TVA et préfixe ; sélection hors de la page courante, marqueur manquant ou falsifié, permissions retirées, modification pendant la transaction, puis réussite après rechargement. Le parcours compilé doit montrer le refus, la saisie conservée et la nouvelle valeur après actualisation. Le diagnostic initial utilise SQL et actions réels, avec session/cache simulés ; il ne constitue pas une preuve navigateur.

La version est un HMAC SHA-256, avec séparation par usage, société et utilisateur, signé avec `AUTH_SECRET` déjà requis pour l'authentification. Elle couvre les valeurs de facturation et leurs références, sans contenir de coordonnées lisibles. Une rotation de cette clé exige de recharger les aperçus ouverts ; aucune nouvelle variable ni migration n'est nécessaire. Le serveur recalcule toujours les lignes depuis SQL, puis les recontrôle dans la transaction sérialisable. Une sélection retirée du périmètre, supprimée ou déjà facturée reçoit le même refus de préparation périmée. Les autorisations restent vérifiées avant toute lecture métier.
